# Phase 02 Plan 08: Admin UI Event Feed (browser-direct nats.ws) Summary

**Admin UI gains an editable-pattern Event Feed pane that subscribes to NATS subjects directly from the browser via the existing wsconnect singleton, with default pattern `mesh.action.>` and a 200-entry capped buffer.**

## Outcome

The Phase 1 admin UI (registry table only) now renders side by side with a live Event Feed. The operator can type any NATS subject pattern (wildcards `*` and `>` supported) and watch decoded messages stream in. Two browser tabs, one cascade: with the scenario UI dispatching from plan 02-04..02-07, the admin tab subscribed to `mesh.action.>` shows the heli / ffunit / medevac status pubsub propagate in real time, completely independent of the dashboard's own /ws bridge. This is the protocol-first proof point for the demo.

## Decoder Contract

`DecodedEvent` shape:

```ts
interface DecodedEvent {
  subject: string;     // full resolved subject (no wildcards)
  payload: unknown;    // JSON-decoded if msg.json() succeeds; otherwise raw string
  raw: string;         // always the raw text payload
  receivedAt: number;  // Date.now() at the moment the message landed
}
```

The render path uses `JSON.stringify(payload)` for non-string payloads and falls back to `raw` if stringify itself throws (defensive).

## Browser-direct invariant

Per ADR-0056 (second amendment) and D-15: the admin UI talks NATS directly over WebSocket via `@nats-io/nats-core`'s `wsconnect`, NOT through any FastAPI / SSE / `/ws` translation layer. This plan honors that contract: `subscribeSubjects` calls `nc.subscribe(pattern)` on the singleton from `ui/src/lib/nats.ts`. The dashboard's `/ws` (ADR-0056 first amendment, plan 02-04) is a separate scenario-UI stack and is intentionally not consumed here.

## Note for plan 02-09 (integration test)

A full event-feed E2E assertion is hard from Python: it would require a headless browser plus a wsconnect mock. The Phase 2 integration test in 02-09 should instead assert that a Python-side side-channel subscription on `mesh.action.>` (e.g. `await mesh._nc.subscribe(...)`) receives messages while the firefighter CLI is dispatching. That covers the protocol-level guarantee. Browser-side correctness is verified manually for the demo recording.

## Threat Model Compliance

The plan's STRIDE register (T-02-08-01..03):

- T-02-08-01 (Information Disclosure on `>`): accepted. Demo is localhost; future enterprise ADR will gate production with auth + per-user ACLs. No code change required for Phase 2.
- T-02-08-02 (Tampering / forged status payloads): accepted. Renderer wraps both `msg.json()` and `JSON.stringify` in try/catch; bad payloads fall back to the raw string. No privileged action is triggered by an event.
- T-02-08-03 (DoS via flood on `mesh.>`): mitigated. `MAX_BUFFER = 200` caps both retained state and React render work; older entries are dropped.
